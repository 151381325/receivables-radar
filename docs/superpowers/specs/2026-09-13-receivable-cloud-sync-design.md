# 回款雷达：云端应收同步设计

**状态：** 已确认，待实施  
**适用范围：** 中国大陆个人自由职业者、单人账号 MVP  
**前置版本：** 已完成账号、会话、PostgreSQL、Docker 与 Caddy 基础设施

## 1. 目标

把现有的应收、到账和跟进记录迁移到账号私有的 PostgreSQL 数据库，使同一账号在电脑与手机浏览器登录后看到一致数据。云端为唯一正式数据源；本阶段不提供离线编辑队列、实时推送或多人协作。

## 2. 用户体验与范围

### 2.1 包含

- 登录后从云端加载当前账号的全部未删除应收记录及其到账、跟进时间线。
- 应收新建、编辑、软删除；到账新增、删除；跟进新增均通过同源 `/api` 完成。
- 成功写入后显示“已同步”；网络或服务器异常时显示“尚未同步”，并保留重试或刷新入口。
- 首次登录时检测旧 LocalStorage 数据；用户确认后先下载 JSON 备份，再批量导入云端。
- 导入时云端已有相同记录 ID 则保留云端版本、跳过本机重复项，并展示导入与跳过数量。
- 同一账号在另一台设备重新打开页面或刷新页面后获得最新云端数据。

### 2.2 不包含

- 离线写入队列、后台补传、字段级合并、WebSocket 实时刷新。
- 多账号协作、组织、角色或共享应收。
- 自动发送催款消息、支付、合同、附件、PWA 与 Android 打包。

## 3. 数据模型

所有业务表均有 `user_id uuid NOT NULL REFERENCES users(id)`，每个查询、更新及删除均以已认证用户 ID 为边界。

| 表 | 关键字段 | 规则 |
|---|---|---|
| `receivables` | `id text`、`user_id`、客户、项目、总金额分、日期字段、`version integer`、`created_at`、`updated_at`、`deleted_at` | `(user_id, id)` 唯一；金额使用整数分；仅 `deleted_at IS NULL` 的记录在常规列表返回 |
| `payments` | `id text`、`receivable_id`、`user_id`、金额分、到账日期、备注、创建时间 | 归属的应收必须属于当前用户；单次及累计到账不得超过应收总额 |
| `follow_ups` | `id text`、`receivable_id`、`user_id`、跟进日期、结果、下次跟进日、创建时间 | 归属的应收必须属于当前用户 |

前端继续使用元作为展示与编辑单位；API 在边界处把元转换为整数分，避免浮点金额计算。`status`、剩余金额、逾期天数与今日行动继续由现有共享领域规则计算，不作为可被客户端任意覆盖的数据库事实。

## 4. API 合约

所有接口均要求已登录，未登录返回 `401`。对象 ID 使用已有前端生成的字符串 ID，避免导入时重新映射关系。

| 操作 | 方法与路径 | 请求关键内容 | 成功结果 |
|---|---|---|---|
| 拉取全部数据 | `GET /api/receivables` | 无 | 当前用户的应收、到账、跟进组成的完整记录数组 |
| 新建应收 | `POST /api/receivables` | 现有应收字段 | 新记录，`version = 1` |
| 编辑应收 | `PUT /api/receivables/:id` | 可编辑字段与 `version` | 更新后的记录，版本加 1 |
| 删除应收 | `DELETE /api/receivables/:id` | `version` | `204`；服务器写入软删除时间 |
| 新增到账 | `POST /api/receivables/:id/payments` | 金额、日期、备注与 `version` | 更新后的完整应收记录，版本加 1 |
| 删除到账 | `DELETE /api/receivables/:id/payments/:paymentId` | `version` | 更新后的完整应收记录，版本加 1 |
| 新增跟进 | `POST /api/receivables/:id/follow-ups` | 日期、结果、下次跟进日与 `version` | 更新后的完整应收记录，版本加 1 |
| 导入旧数据 | `POST /api/receivables/import` | 已验证的本地记录数组 | `{ importedCount, skippedCount, records }` |

服务端把无归属记录、软删除记录和其他账号记录统一表现为 `404`，防止泄露记录是否存在。编辑、删除、到账与跟进请求的版本低于当前版本时返回 `409 CONFLICT`，响应包含稳定错误代码 `STALE_VERSION`，不写入数据。

## 5. 前端数据流

1. 认证完成后，页面调用 `GET /api/receivables`，加载期间显示“正在同步你的数据”。
2. 页面内存仓库保存最近一次成功读取的云端记录，所有现有统计、筛选、日历和文案仍读取这一仓库。
3. 用户操作先禁用对应提交按钮并调用 API；只有 API 成功后才用响应记录更新仓库、重新渲染并提示“已同步”。
4. 网络或 `5xx` 失败时，不改变内存仓库，提示“尚未同步”，提供重试当前操作和刷新数据入口。
5. `409 STALE_VERSION` 时，自动重新拉取云端数据，提示“另一台设备已更新，请确认最新内容后再操作”。
6. 用户退出时清空内存中的云端记录并返回登录页；浏览器中保留旧 LocalStorage，作为用户自行备份来源。

## 6. 旧数据迁移

首次云端数据成功加载后，前端检查 `receivables-radar.records` 中是否存在可解析的旧记录。若存在，显示记录数量及两个选择：

- “备份并导入”：立刻使用现有备份格式下载 JSON，再调用导入接口。
- “暂不导入”：不上传、不删除本机记录；设置一个本机提示标记，之后可在设置入口再次发起导入。

导入接口在单个数据库事务中逐条验证记录。云端已有相同 `(user_id, id)` 的记录时跳过，不覆盖云端数据。导入成功后前端使用接口返回的完整云端记录替换内存仓库，并告知导入、跳过数量；下载或导入失败时不得标记迁移完成。

## 7. 错误处理与安全

- 输入校验在前端保留现有体验，但服务端必须重新验证文本长度、日期、金额、关联关系、到账上限和版本号。
- SQL 必须参数化；任何业务查询都必须带 `user_id`。
- 软删除应收后，其到账与跟进数据不再从普通 API 返回；恢复功能不在本阶段范围内。
- 导入接口限流并限制单次最多 500 条记录，避免超大浏览器数据造成资源耗尽。
- 页面不显示原始错误、数据库信息、Cookie 或令牌；日志避免记录业务备注与密码。

## 8. 验收与测试

- 两个测试账号互相无法读取、修改、删除或向对方记录新增到账/跟进。
- 新建、编辑、删除、到账、删除到账、跟进后，云端返回的数据保持现有领域规则。
- 旧版本写入收到 `409 STALE_VERSION`，且数据库记录不变。
- 导入自动触发本地 JSON 备份；相同 ID 跳过，其他记录导入，不出现重复。
- 网络失败不将操作显示为已保存；手动刷新可恢复最后一次成功云端状态。
- `npm test`、`npm run build`、Docker 全栈 `/api/health` 通过；桌面与 390px 手机宽度下同步提示清晰可用。

## 9. 实施顺序

1. 新增迁移、服务器仓库与受保护 API，先用 PostgreSQL 集成测试证明数据隔离与版本冲突。
2. 以云端仓库替换浏览器业务数据来源，接入同步状态与错误恢复。
3. 实现确认式旧数据导入与备份下载。
4. 进行双账号、双设备模拟、桌面/手机 UI 与 Docker 全栈验收。
