# 回款雷达功能检查与 VIP 预留方案

检查日期：2026-10-14。范围：本地 main 分支、Android 工作树原生入口、现有自动化测试及线上公开健康接口。当前确认的视觉方向为 `previews/fintech-ui.html` 的整体科技风；它仍是独立示例预览，未接入正式业务。

## 结论与边界

产品已具备应收记录、跟进、到账、结清、模板文案、账号和云端同步的基础闭环，但不能认定为功能全部验收。优先解决任务准确性、到账纠错、导入校验与账号恢复，再增加易找、易跟进、易复用的功能。付费版销售效率与专业输出，免费版必须能独立完成核心回款工作。

APP 使用 Capacitor 加载 `https://huikuanleida.cn`，大部分界面与业务跟随线上网站。Android 目前没有注册业务原生插件；本次未连接手机，不能认定文件下载、日历导入、后台提醒、系统返回、重连行为已经通过真机验收。桌面图标、包名与正式签名材料不在本次修改范围。

## 优先修复

| 优先级 | 问题或缺口 | 处理建议与验收 |
|---|---|---|
| P0 | 多设备同时登记到账时，仓库先查版本再写入，但没有行锁或条件更新保证整个操作串行；存在超收风险 | 使用记录行锁或等效原子并发控制。隔离测试库中并发登记两次，确保仅一笔成功或累计不超过总额；此项为代码风险，尚未在数据库中复现 |
| P0 | API 导入仅检查数组长度，上游前端验证不覆盖直接请求；日期、子记录、累计到账等未完整校验 | 服务端逐笔规范化并验证日期、金额、子记录和累计已收，非法批次不写入；验证回滚与账号隔离 |
| P0 | 到账录错后用户无法纠正 | 打通删除误录到账的界面、客户端、路由、版本检查；明确金额变化，保留审计；已结清记录纠错后可恢复待收 |
| P1 | 逾期条目今日已跟进，安排未来跟进日，仍 needsActionToday=true | 区分“风险仍存在”与“今天还需要行动”；风险金额继续显示，安排未来跟进后今日清单合理退出；新的承诺违约等事件可重新进入 |
| P1 | 最新跟进 promiseDate=null，仍反向查到旧承诺日期 | 明确空值语义。采用明确的保留/更新/撤销承诺操作，避免未填写被误认为撤销；测试最新有效承诺与撤销场景 |
| P1 | 验证邮件 30 分钟过期后没有重发入口；重复注册被 EMAIL_EXISTS 拦截 | 增加重发验证邮件与限流，提示垃圾邮件检查，验证停用状态与令牌替换 |
| P1 | 退出请求失败被吞掉后刷新，Cookie 可能仍有效，用户会再次进入 | 明确反馈退出失败，保留可重试入口；安全清理当前账号界面与内存数据 |
| P1 | 回到页面、APP 恢复前台、网络恢复不自动拉取；跨天待办也可能陈旧 | 在可见性恢复、联网恢复、日期变化时刷新；请求去重、防止旧请求覆盖新结果；冲突失败时不能声称已刷新成功 |
| P1 | 导入前备份下载的是所选文件 source，而非当前云端记录 | 备份当前 repository.list()，提示导入是新增合并，不是完整覆盖恢复；同 ID 保留和软删记录行为写清楚 |
| P1 | 空列表共用“新建第一笔”引导 | 区分新账号、今天无任务、筛选无结果，并给相应入口 |
| P1 | APP 文件/日历导出使用网页 Blob 下载，无业务原生桥接 | 真机验收保存 JSON、选择导入 JSON、导入 ICS、复制文案；有失败则实现必要的原生保存/分享入口 |
| P1 | APP -2A 备案号未在所查界面展示 | 在 APP 的关于页展示用户提供的渝ICP备2026023184号-2A及查询链接，网站 -1 保留；发布前核对 |

### 已复现的任务行为

1. 应收截止 2026-10-01，2026-10-14 添加跟进并设置下次跟进为 2026-10-17：deriveReceivable 仍返回 needsActionToday=true，reason=已逾期13天。
2. 原承诺 2026-10-12，最新跟进 promiseDate=null：deriveReceivable 仍返回 latestPromiseDate=2026-10-12、promiseOverdue=true。现有表单没有区分“未修改”与“主动撤销”，需设计明确操作而不是简单清空历史承诺。

## 免费版：少入口、完整闭环

主导航只保留“今日、应收、我的”；新增应收是明确主按钮。首页强调真实待办、风险与最近动态，不在主流程堆放付费推广。

| 能力 | 免费版范围 |
|---|---|
| 记录 | 创建、编辑、暂停、结清、基础客户记忆；新增默认只显示客户、项目/用途、金额、到期日，其他字段折叠 |
| 处理 | 跟进、下次日期、承诺管理、部分到账、到账纠错、编辑确认 |
| 查找 | 客户/项目搜索，逾期/即将到期/状态筛选，金额/日期排序，列表合计 |
| 回访 | 准确今日清单、合理处理完成反馈、最近动态、基础提醒和模板复制 |
| 数据 | 账号同步、基本备份导出与导入、密码恢复、注销入口、隐私和备案信息 |

长期使用的可验证目标是“用户能迅速录入、找到下一步、处理后看到进展、避免漏跟进”，不是用动效或锁住数据强迫回访。活跃与留存需要上线后的真实使用验证，目前不能承诺。

## 技术预留方案（尚未实现）

1. 设置稳定 feature code 与“未发布 / 内测 / 已发布”状态，和账号权益分开管理。
2. 服务端提供权益快照，如 plan、有效期、features；权益来源、变更与到期留审计。当前没有这套系统，不能把静态 VIP 标志当作权限。
3. 在每个付费服务端接口检查真实权限；前端只负责展示提示，隐藏按钮不等于鉴权。没有登录或权限时默认拒绝付费接口。
4. 到期后仍允许查看、编辑核心记录与导出数据；关闭未获授权的高级任务，提醒状态不能伪装成功。
5. 支付开通留到实际商品上线：订单、回调验签、幂等、退款、权益到期、渠道订阅规则需单独验收。当前不加付款按钮，不承诺价格。
6. “我的”中可放一个安静的高级功能介绍入口，未发布能力标明“规划中”，不让用户为不可用服务付费。
